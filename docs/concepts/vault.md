# Vault

## The Problem

Applications need secrets:

```text
database password
API key
JWT signing key
```

The simple Kubernetes-only way is:

```text
Kubernetes Secret
  -> app reads it
```

That works, but it does not answer the bigger production questions:

```text
who owns the secret?
who rotated it?
who read it?
can the secret expire automatically?
can we create short-lived database users?
```

Vault solves those problems by becoming the source of truth for secrets.

## What Vault Is

Vault is a secrets manager.

In this project:

```text
Vault stores:
  secret/task-api/config
    username=task-user
    password=<task-api-password>

  secret/task-service/db
    username=<task database user>
    password=<task database password>

  secret/task-service/redis
    REDIS_PASSWORD=<redis password>

  secret/kibana/encryption-keys
    securityEncryptionKey=<stable key>
    savedObjectsEncryptionKey=<stable key>
    reportingEncryptionKey=<stable key>
```

Vault decides access using:

```text
auth method
  -> who are you?

policy
  -> what paths can you read/write?
```

## Kubernetes Secret Vs Vault

Kubernetes Secret values are base64 encoded.

```text
base64 = encoding
not encryption by itself
```

Vault gives stronger secret workflows:

```text
central ownership
access policies
audit logs
rotation
dynamic secrets
short-lived tokens
```

## Direct Vault Flow

This is the first flow we tested.

```text
pod with ServiceAccount vault-secret-reader
  -> Kubernetes mounts ServiceAccount JWT
  -> pod sends JWT to Vault
  -> Vault checks JWT with Kubernetes
  -> Vault maps JWT to role task-api
  -> role gives policy task-api-read
  -> pod reads secret/data/task-api/config
```

Important objects:

```text
ServiceAccount vault-secret-reader
  -> Kubernetes identity for the pod

Vault Kubernetes auth
  -> lets Vault trust Kubernetes ServiceAccount tokens

Vault role task-api
  -> binds ServiceAccount to Vault policy

Vault policy task-api-read
  -> allows read on secret/data/task-api/config
```

In this flow, the app or pod talks to Vault directly.

## ESO Flow

ESO means External Secrets Operator.

ESO is a Kubernetes operator that copies secrets from external systems into Kubernetes Secrets.

In this project:

```text
Vault
  -> ESO
  -> Kubernetes Secret task-api-config
  -> app reads Kubernetes Secret
```

Important objects:

```text
SecretStore vault-task-api
  -> tells ESO how to connect to Vault

ExternalSecret task-api-config
  -> tells ESO which Vault secret to copy

Kubernetes Secret task-api-config
  -> generated by ESO
```

In this flow, the app does not talk to Vault directly.

## The Full Flow We Built

```text
1. Vault stores secret/task-api/config

2. Vault Kubernetes auth trusts Kubernetes ServiceAccount tokens

3. Vault role task-api trusts:
     ServiceAccount: vault-secret-reader
     Namespace: task-api

4. Vault policy task-api-read allows:
     read secret/data/task-api/config

5. ESO SecretStore logs into Vault using that Kubernetes identity

6. ESO ExternalSecret reads:
     task-api/config.username
     task-api/config.password

7. ESO creates Kubernetes Secret:
     task-api-config

8. Pod reads:
     task-api-config.username
     task-api-config.password
```

## Real App Flow

For task-service we now use Vault as the source of truth:

```text
Vault secret/task-service/db
Vault secret/task-service/redis
  -> ESO ExternalSecret
  -> Kubernetes Secrets:
       task-service-db-from-vault
       task-service-redis-from-vault
  -> task-service env vars:
       POSTGRES_USER
       POSTGRES_PASSWORD
       REDIS_PASSWORD
```

The app does not know Vault exists.
It still reads environment variables from Kubernetes Secrets.
ESO is the bridge between Vault and Kubernetes.

Kibana uses the same pattern for static encryption keys:

```text
Vault secret/kibana/encryption-keys
  -> ESO ExternalSecret kibana-encryption-keys
  -> Kubernetes Secret kibana-encryption-keys
  -> Kibana env vars:
       XPACK_SECURITY_ENCRYPTIONKEY
       XPACK_ENCRYPTEDSAVEDOBJECTS_ENCRYPTIONKEY
       XPACK_REPORTING_ENCRYPTIONKEY
```

The Kibana service token is still generated/stored as a Kubernetes Secret because it belongs to the Elasticsearch/Kibana integration lifecycle.

## Static Vs Dynamic Secrets

Static secret:

```text
username/password stored in Vault
ESO syncs it into Kubernetes
```

Dynamic secret:

```text
app asks Vault for database credentials
Vault creates temporary DB user
credentials expire automatically
```

Interview answer:

```text
Static secrets are simpler.
Dynamic secrets are more production-grade for databases.
```

## Local Vs Production

This repo uses Vault dev mode for learning.

Dev mode:

```text
root token is a local dev value
data is in memory
not HA
not secure
```

Production Vault needs:

```text
HA Vault cluster
TLS
persistent encrypted storage
auto-unseal with cloud KMS or HSM
audit logs enabled
least-privilege policies
root token not used by apps
backup and restore tested
rotation drills
monitoring for sealed/unsealed state
```
